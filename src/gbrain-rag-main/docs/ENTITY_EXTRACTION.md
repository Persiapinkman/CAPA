# gbrain-rag 实体抽取说明

最后更新：2026-05-09

## 概述

当前 `gbrain-rag` 的实体抽取采用确定性规则实现，不调用 LLM。它的目标不是做开放域命名实体识别，而是面向 RD 模型知识库，稳定抽取对检索排序有帮助的模型名、版本号、OID、部署 ID、平台和领域短语。

核心代码位于：

- `src/gbrain_rag/retrieval/entities.py`
- `src/gbrain_rag/retrieval/store.py`
- `src/gbrain_rag/retrieval/service.py`

## 抽取流程

### 1. 文本归一化

实体抽取入口是 `extract_entities(text)`。系统会先调用 `normalize_text` 对输入文本做归一化，减少空白、大小写和格式差异对规则匹配的影响。

入库阶段的输入文本由以下内容拼接而成：

- `doc_name`
- `title`
- `text`
- `index_text`

这样可以同时利用文档名、标题、正文和索引增强文本中的实体信息。

### 2. 强结构实体抽取

系统使用正则表达式抽取以下强结构实体：

| 实体类型 | 含义 | 示例 |
| --- | --- | --- |
| `model` | 模型文件名 | `KM_classifier_safety_rope_nart_cuda11.0-trt7.1-int8-T4_b16_0.2.1.model` |
| `version` | 版本号 | `v0.2.1`、`3.0.1`、`2.55.1` |
| `oid` | 模型 OID | `a6192abca7ab016a58072578cd61b7ad2ee6637ed9e05cca1e49e390b6bddb60` |
| `deployment` | 部署/发版 ID | `did=100634`、`rid=51554` |
| `platform` | 硬件和推理平台 | `cuda11.0-trt7.1-int8-T4`、`acl-ascend710-fp16` |

这类实体通常是模型发版和部署问答中的关键定位信息，适合用规则稳定抽取。

### 3. 领域短语抽取

除强结构实体外，系统还抽取两类中文领域短语：

| 实体类型 | 含义 | 示例 |
| --- | --- | --- |
| `field` | 字段或属性名 | `输入`、`输出`、`阈值`、`标签`、`负责人`、`推荐配置` |
| `scene` | 场景、任务或模型类别短语 | `人脸检测`、`人脸特征`、`烟火识别`、`道路积水检测`、`结构化模型` |

这部分主要用于提升短查询和字段查询的排序效果。例如用户问“文搜图模型的特征维度是多少”，`特征`、`模型` 等短语会帮助相关 chunk 获得图信号和字段信号加权。

### 4. 去重和截断

抽取出的实体会按 `(kind, normalized_name)` 去重。默认每段文本最多保留 `36` 个实体，避免单个 chunk 中实体过多导致图信号过宽、排序噪声变大。

## 入库阶段如何建图

入库时，`BrainStore._refresh_chunk_entities` 会为每个 chunk 执行实体抽取，并写入 SQLite：

| 表 | 作用 |
| --- | --- |
| `entities` | 保存实体本身，包括类型、原始名称和归一化名称 |
| `chunk_entities` | 保存 chunk 与实体的关联 |
| `entity_links` | 保存实体之间的共现边 |

当前 `entity_links` 的关系类型是 `co_mentions`。如果两个实体出现在同一个 chunk 中，就建立共现关系，并累加 `evidence_count`。

例如某条安全绳模型记录中同时出现：

- `safety_rope`
- `v0.2.1`
- `cuda11.0-trt7.1-int8-T4`
- `100634`

这些实体会共同挂到同一个 chunk 上，并形成共现边。这相当于一个轻量知识图谱，用于增强检索排序。

## 查询阶段如何使用实体

查询时，系统会对用户 query 使用同一套规则抽取实体，然后与候选 chunk 的实体做重叠度计算。

流程如下：

1. 先执行向量召回和关键词召回，得到候选 chunk。
2. 从 `chunk_entities` 读取候选 chunk 已抽取的实体。
3. 对 query 实体和 chunk 实体计算 overlap score。
4. 将该分数作为 `graph_score`。
5. `graph_score` 进入 RRF 融合，并对最终 fused score 做加权 boost。
6. 返回证据时保留 `matched_entities` 和 retrieval signals，便于审查排序原因。

当前 overlap 计算方式较简单：

```text
overlap_score = query 与 chunk 共有实体数 / query 实体数
```

这个分数可解释性强，也不会引入额外模型推理成本。

## 对检索的作用

实体抽取主要提升以下问题类型：

- 精确模型查询：模型名、版本号、模型文件名。
- 字段查询：OID、负责人、推荐配置、特征维度。
- 部署查询：did/rid、平台、T4/P4/Ascend 等部署信息。
- 推荐类问题：通过场景短语和领域别名定位候选模型。
- 跨源核对：同一模型、版本、平台或部署 ID 在文档、表格和 Adela 中的关联。

相比只依赖向量召回，实体图信号对短查询、型号查询和 ID 查询更稳定。例如：

- “安全绳检测，在 T4 平台上有部署的模型吗”
- “请帮我找出人脸特征模型，适配 T4 的模型 oid”
- “城市结构化检测模型 3.0.1 是最新的吗”

这些问题中的 `T4`、`oid`、`3.0.1`、模型类别和部署 ID 都适合由规则实体参与排序。

## 当前边界

当前实体抽取是轻量规则图谱，不是完整知识图谱系统：

- 不调用 LLM 做开放域实体识别。
- 不做复杂实体消歧，例如同名模型族的层级关系仍依赖字段和文本。
- `entity_links` 目前主要表示共现关系，不表达“属于”“部署于”“新版本替代旧版本”等复杂语义关系。
- 图信号只用于检索增强和排序，不做多跳图推理。
- 抽取效果依赖正则和领域词表，新增业务类型时需要补充规则。

这个设计是有意选择的：在 RD 模型知识库场景中，很多关键事实本身具有明确格式，规则抽取更快、更稳定，也更容易解释和维护。

## 后续优化方向

可以考虑逐步增强以下能力：

- 增加模型族归一化，例如把 `SmallFace_Gray_800x1333`、`Face_Gray_4.15.3` 关联到同一模型族。
- 增加关系类型，例如 `deployed_on`、`has_version`、`has_oid`、`replaces`。
- 对 table/adela metadata 做字段级实体抽取，而不仅依赖拼接文本。
- 引入别名表，将中文任务名和英文模型名稳定映射。
- 对跨源核对类问题增加版本时间线和部署状态推理。
