# document 模型发版文档正文问答 v1 简介与耗时

## v1 简介

当前的 `document` 文档问答 v1 是一个典型的“检索 + 大模型生成”链路。这里的 `document` 指模型发版文档正文内容，来源于 ONES 工作文档及对应发版 PDF。接口流程如下：

1. 接收用户问题
2. 使用 embedding 模型对问题做 query embedding（默认 `EvoQwen2.5-VL-Retriever-3B-v1`）
3. 在 Milvus 向量库中检索相关文本块
4. 对检索结果做去重（多模型场景下会做融合）
5. 将检索结果拼接成上下文，调用大模型生成最终回答
6. 对命中的 PDF 来源链接做去重与映射
7. 返回回答、检索结果、reference，以及分步耗时 `timings`

当前接口已经支持：

- 在响应中返回 `retrieve_ms`、`answer_ms`、`reference_ms`、`total_ms`
- 在服务端将每次调用的分步耗时落盘为 JSONL，便于后续统计分析

## 各过程使用的方法

### 1. 请求接入与总耗时统计

- 接口入口为单次问答 API `/api/v1/rag/chat_engine/query`
- 在路由层按阶段分别统计：
  - 检索耗时 `retrieve_ms`
  - 大模型回答耗时 `answer_ms`
  - reference 处理耗时 `reference_ms`
  - 总耗时 `total_ms`
- 最终这些耗时会同时：
  - 写入接口响应 `timings`
  - 写入服务端 JSONL 日志，方便后续聚合分析

### 2. 查询向量化

- 当前默认使用单个 embedding 模型：`EvoQwen2.5-VL-Retriever-3B-v1`
- 对同一个用户问题，默认只生成一份 query embedding
- 如果显式传入多个 `embedding_models`，会分别生成多份 query embedding

### 3. 向量检索

- 向量库使用 Milvus
- 默认单模型场景下只发起一次向量检索
- 多模型场景下，每个 embedding 模型会单独发起一次向量检索
- 检索条件中会附带 `embedding_model == 当前模型名`，确保查询和对应模型写入的数据匹配
- 每路检索会按 `top_k` 返回候选结果
- 检索后会做一次结果清洗与去重，避免重复 chunk 进入后续流程

### 4. 多模型结果融合（可选）

- 默认单模型场景不需要融合
- 当请求里传入多个 embedding 模型时，检索结果不会直接拼接，而是做融合
- 当前融合方法是 `RRF`（`Reciprocal Rank Fusion`）：
  - 分别看每一路结果中的排序位置
  - 根据排序位置计算融合分数
  - 对多路结果重新排序，得到统一候选集
- 融合后再按阈值 `similarity_threshold` 过滤，保留最终进入回答阶段的文本块

### 5. 上下文构造

- 回答阶段不会只传用户问题，而是会把检索结果格式化成一个统一的 prompt
- 当前每个命中 chunk 会拼接以下信息：
  - `doc_name`
  - `header`
  - `heading`
  - `score`
  - `index_text`
- 这里的 `index_text` 是父级大文本块内容，不只是小 chunk 本身
- 这种做法的优点是信息更完整，缺点是 prompt 较长，会明显增加回答耗时

### 6. 大模型回答生成

- 回答生成通过 OpenAI 兼容接口调用
- 当前默认回答模型配置为：
  - `model: Qwen3.5-4B`
  - `base_url: http://10.111.32.253:8000/v1`
- 调用方式是非流式单次生成
- `enable_thinking` 当前显式关闭，不走思维链展示
- 回答 prompt 的核心约束包括：
  - 只能基于检索到的 `<context>` 回答
  - 如果知识库中没有相关信息，要明确返回“未找到”
  - 尽量引用与问题直接相关的内容

### 7. reference 处理

- 回答生成完成后，会从检索命中的 chunk 中提取 `doc_name`
- 然后按 PDF 文件名做去重
- 来源链接映射来自 `data_source/pdf_reference_links.csv`
- 映射规则支持：
  - 完整文件路径匹配
  - 文件 basename 匹配
- 最终返回结构为：
  - `doc_name`
  - `url`

### 8. 耗时记录落盘

- 每次单次问答请求都会记录一条结构化 JSONL
- 记录内容包括：
  - query
  - embedding_models
  - retrieved_count
  - reference_count
  - answer_length
  - 各阶段耗时 `timings_ms`
- 这部分可以直接用于后续做：
  - 平均耗时统计
  - P50 / P95 / Max 分析
  - 不同问题类型或不同模型组合的对比分析

## 结论

从当前统计结果看：

- 客户端额外开销很小（avg `3.334ms`），端到端耗时几乎由服务端耗时决定
- 服务端耗时仍主要由回答阶段决定（`answer_ms` 占 `total_ms` 约 86.2%）
- `reference` 处理耗时可以忽略不计（avg `0.120ms`）
- 检索阶段已经稳定在亚秒级（avg `252.755ms`），但不同问题的回答耗时差异明显（与回答长度强相关）

因此，后续若要继续优化整体响应时间，优先方向应放在：

- 缩短传给大模型的上下文长度，尤其是减少 `index_text` 带来的长 prompt
- 降低回答生成的 token 数
- 优化提示词与回答策略，减少冗长输出
- 使用更快的回答模型或更高吞吐的推理服务
